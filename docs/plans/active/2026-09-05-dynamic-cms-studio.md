## Goal

Eric can sign in to `/studio` with a passkey from any device, write and edit blog posts and Leetcode solutions in a block editor (headings, lists, quotes, tables, callouts, footnotes, math, images with required alt text, code blocks with language/filename/line-highlight/diff, multi-language code tabs, complexity badges), autosave with restorable revisions, upload photos, and publish or unpublish instantly — while readers see fast cached pages at `/blog/[slug]` and `/leetcode/[slug]`, the five most recent posts in the home `#blog` tile with a link to the paginated index at `/blog`, and the home page's contracts, motion, and personality remain untouched.

- Migrating the changelog off its hand-authored TypeScript source or changing `/changelog.xml`.
- Full-text search, related-post suggestions, or an OG-image generator (candidate follow-ups).
- Scheduled publishing, slug-change redirects, and share-link expiry (deferred; `published_at` stays a nullable timestamp so scheduling can be added later).
- Studio access on preview deployments (WebAuthn origin binding; production and `localhost` only).
- Changing the home document structure, tile contract, or motion systems.
- A separate CMS service or third-party content platform.

## Publishing and data safety

- **Draft/public separation:** keep one working draft with a monotonically increasing version, immutable durable revisions, and a nullable published-revision reference. A published revision captures body, per-collection metadata, and media references including contextual alt text/captions. Public pages, metadata, indexes, and home read only this snapshot; preview uses a separately authorized draft read. Keep nullable `published_at` and a permanent first-publication marker so unpublish cannot unlock the slug.
- **Atomic transitions:** publish validates the expected draft version and creates/selects a complete revision in one database transaction; republish does the same. Unpublish clears visibility without destroying the draft/history. Explicit save creates a revision; autosave does not. Restore writes a new working-draft version, never the published snapshot. Draft edits must not overwrite previously published media objects in place.
- **Conflicts/retries:** version-check autosave, explicit save, restore, publish, and unpublish. Reject stale operations from another tab/device or out-of-order request, retain local edits, and show actionable unsaved/conflict states. Make mutation retries idempotent so a lost response after commit cannot duplicate publication revisions or undo a newer decision.
- **Format evolution:** include `schema_version` in documents, revisions, and exports. Define supported versions, lossless migrations, and old-document fixtures before extending the schema. Preserve and explicitly reject unsupported versions/blocks rather than silently stripping content. Content exports/imports preserve draft/public separation and media references and exclude credentials, sessions, and share/enrollment secrets.

## Cache and failure contract

- **Handler proof:** step 3 selects `'use cache'` or `'use cache: remote'` after inspecting the actual hosting adapter/cache handler. Default in-memory caching does not establish persistence or shared invalidation in serverless hosting. Record lifetimes and tag coverage for detail/metadata, missing-slug lookups, both collections and their paginated indexes, and home. The sitemap and RSS stay static and outside this invalidation set. Cache hits can hide database latency; cold/missing/expired entries cannot.
- **Five-second boundary:** from a successful publish/republish/unpublish acknowledgment, fresh anonymous requests to affected canonical URLs must receive the new state within 5 seconds. Use an independent browser/request context without author/draft-mode cookies or cache-busting URLs. This is request freshness, not push updates to already-open tabs or erasure of browser history/downloads. Cover warm/cold caches, a cached 404 followed by publish, and unpublish after warming. Local `next start` is not hosted cross-instance evidence; verify the actual deployed handler and multi-instance behavior where supported, or leave that release gate blocked.
- **Partial failure:** database commit and cache invalidation are not atomic. Record retryable pending-sync state; report fully published/unpublished only after commit and required invalidations succeed. A committed write followed by failed invalidation needs an actionable sync-pending error, not success or a claim that nothing was saved. Test failure after commit and idempotent retry. Document how pending invalidations recover without relying on a discarded serverless process.
- **Outages:** use bounded database timeouts and explicit failure states. Home renders a fixed-height “posts unavailable” state, distinct from empty/loading, while static sections remain usable. Detail/index failures must not masquerade as missing content or be cached as successful empty data. Never resurrect a known unpublished snapshot from an invalidated entry during an outage. Test failure/recovery with warm and cold caches and verify tile positions as well as height.

## Security and environment contract

- **Environment matrix:** production uses the configured canonical origin/RP ID and production database. Local development/CI use an explicit server-controlled local/test mode, loopback listener, `localhost` origin/RP ID, and isolated Postgres; the auth Playwright project must use `http://localhost:3100`, not the current `127.0.0.1` origin. Preview/other deployments 404 studio and its auth/upload/authoring endpoints. Do not enable local mode based only on a supplied Host header or fake `VERCEL_ENV=production` in tests. Each operation enforces environment policy as well as auth; hiding pages in `proxy.ts` is insufficient.
- **Enrollment/recovery:** login and token-gated enrollment are the anonymous exceptions in allowed environments, avoiding redirect loops. Every enrollment requires the set, matching token; normal additional-credential enrollment also requires an owner session. Token-gated bootstrap/lost-session recovery is the explicit session exception. Preserve set/enroll/unset, document its platform redeploy cost, and support revoking lost credentials and existing sessions. Use a maintained WebAuthn verifier with server-controlled, short-lived, single-use challenge state (a row or integrity-protected cookie plus replay protection), origin/RP ID and user-verification checks; never trust a client-supplied expected challenge.
- **Authorization:** guard every authoring read/mutation and upload handler, not only the layout; route handlers also enforce CSRF. Reject unauthorized draft bodies, metadata, revisions, exports, and media, not merely their listings. Validate safe document URLs/markup as well as JSON shape. Tests include wrong/unset enrollment tokens, expired/replayed challenges, wrong origin/RP ID, and expired/revoked sessions, alongside successful sign-in and recovery.
- **Draft sharing:** non-expiring per-post bearer tokens remain revocable by regeneration. Store token hashes, redact secrets from logs, prevent referrer leakage, and keep preview responses out of shared caches/search/sitemaps. Check authorization on every preview/private-media request. Test missing/invalid tokens, a token for another post, and a regenerated old token. Revocation prevents future requests, not copies already downloaded.
- **Media:** define private-draft versus public-published delivery before choosing storage/upload details. Presigned uploads are short-lived and restricted to authorized keys, allowed types, and sizes; verify the completed object before attachment/publication. Unpublished-only assets must not leak through public object URLs or the image optimizer. Publishing may expose referenced immutable assets; unpublish cannot retract already-public cached copies. Test signing/finalization auth and CSRF, oversized/disallowed uploads, wrong object keys, and direct storage/optimizer access to private media.
