# CMS foundations (not a publishing service)

[ADR-0002](../decisions/0002-dynamic-content-and-hosted-studio.md) is accepted. Step-2 slices add portable content and [auth-data contracts](studio-auth-foundations.md) plus migration artifacts, **not** a studio, runtime connection, public renderer, editor, working authentication, publication transaction or cache worker. Nothing in `app/` or shared public components imports `cms/`. Public routes, placeholders, redirects, sitemap, motion and changelog/RSS remain unchanged. Progress and exact evidence live in [the active plan](../plans/active/2026-09-05-dynamic-cms-studio.md).

**Current provider foundation (2026-09-06):** Eric selected **Neon Free**, confirmed Vercel and requires $0 spending. The bounded provider slice replaced the unused Supabase surface with a standard `pg`/verified-TLS Neon adapter while retaining shared transactions, local isolation and all SQL artifacts. Sixteen Neon factory/configuration cases are offline; the 19-test fresh/replay suite is real local direct PostgreSQL evidence, not hosted Neon/PgBouncer proof. Normal Neon inactivity auto-wakes, but cold starts, free-quota suspension, outages and independent recovery remain gates. Neon Auth/Data API/Storage/Functions and paid features are not selected. Least-privilege roles and no alternate API access to private CMS/auth tables remain provisioning prerequisites.

## Format boundary

A stored body is `{ schema_version: 1, doc: { type: "doc", content: [...] } }`. Only `doc` is native editor JSON; its version envelope must be retained separately around future `getJSON()`/`setContent()` calls. Those calls are not implemented or tested yet.

- Paragraphs and headings contain plain text nodes only. Empty textblocks may omit `content` or retain `[]`; the root requires at least one textblock. Headings require `attrs.level` 2, 3 or 4; the title will supply h1.
- All objects are strict, including attributes and text nodes. No defaults, coercion, trimming, sanitization or dropped unknown keys. Marks (including links/bold), raw HTML, hard breaks, images and later block families are explicitly unsupported. Rejection is **not** proof of future URL/HTML renderer safety.
- Limits: 2,000 blocks, 2,000 text nodes per block, 100,000 characters per text node and one million characters total. Future request handlers must also bound raw request bytes before parsing; these limits alone do not protect a network endpoint.
- `readDocument` returns the original input on unsupported-version or invalid/unsupported-content failure. Preserve it for recovery; never replace it with an empty document or log the result (private content). Direct zod validation also rejects instead of stripping, without mutating the supplied input.
- Metadata has its own version and discriminant: Blog requires `title` and calendar `date`; Leetcode additionally requires `number`, `difficulty` (`Easy`/`Medium`/`Hard`), `language`, `time_complexity`, `space_complexity`, and a `learnings` array (which may be empty). Text is preserved, dates are real `YYYY-MM-DD` calendar dates, and no cross-collection fields are accepted.
- The Leetcode test fixture is only the field specimen already verified in the plan: 2429 Minimize XOR, Medium, 2025-01-15 (URL date; source time was empty), C++, `O(log n)`, `O(1)`, `__builtin_popcount`. No source posts or solution bodies were imported, seeded into a real database or published.
- A version-1 snapshot groups `body`, `metadata` and `media`. `media` must currently be `[]`; silently accepting references without executable image support would lose information. The media slice must add versioned references and contextual alt/captions together with its editor/renderer/privacy tests.

`tests/cms/fixtures/document-v1.json` is the first compatibility fixture, not a fabricated older format. Only version 1 is supported; there is no old-version migration to claim yet. Freeze this fixture. Future schema changes require explicit version support, lossless migrations and old-fixture tests before enabling new blocks. Full versioned export/import and the checksummed media manifest remain future release work.

## Persistence boundary

| Table                    | Model and intended constraints                                                                                                                                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `posts`                  | One complete working `draft` JSONB snapshot, `draft_schema_version`, `draft_version`, all-mutation `version`, collection/slug, permanent `first_published_at`, nullable `published_at` and `published_revision_id`                        |
| `revisions`              | Durable immutable snapshot, explicit `schema_version`, source `draft_version`, same-collection post identity; one revision per post/draft version so explicit save and publish can reuse it                                               |
| `publication_operations` | Idempotency key, server-computed canonical request hash, expected post/draft versions, exact result version, selected revision (null for unpublish), required invalidation tags, pending/synced state, attempt count and retry timestamps |

The nullable publication pointer uses a **same-post composite foreign key**, not just a revision UUID. Publication timestamp and pointer agree; public reads will select only the immutable revision. JSONB is typed `unknown` on reads, not asserted to be valid content. SQL checks verify envelope version/collection consistency and positive versions while preserving future JSON; zod must validate complete snapshots at every later read/write boundary. Unknown/future data must remain recoverable even when an old reader cannot render it.

Custom migration `0001_cms_integrity.sql` supplies invariants Drizzle snapshots do not represent:

- UPDATE/DELETE of revisions is rejected; foreign keys have no cascading history deletion.
- Post identity/collection is fixed; once first published, neither the slug nor the first-publication marker can change, even after unpublish.
- Each post update advances `version` exactly once. Draft changes additionally advance `draft_version`; restoring identical content may also advance it. Publish/unpublish can therefore conflict without changing the draft. Counters are positive PostgreSQL integers; overflow fails rather than wraps.
- Publication receipt identity/result/tags cannot change or be deleted. Only retry progress may change; attempts cannot decrease and a synced receipt cannot return to pending.

These guards now have **local PostgreSQL 17.11 integration evidence**: all four unchanged migrations applied/replayed, content/auth constraints passed, and fixture rollback preserved all seven tables' pre-test row counts. `pnpm test:cms:docker` supplies a disposable loopback-only target with a non-superuser DDL role; the separate CI database job now uses that same command, but no hosted CI run or runtime database is claimed. Triggers do not replace authorization, least-privilege roles (including denying truncate/DDL), or transactional expected-version predicates. Never use `drizzle-kit push` in place of the append-only migration chain; it cannot reconstruct these custom guards.

## Interactive transaction adapter (foundation only)

`createLocalPgDatabase(url, limits?)` and `createNeonDatabase({ connectionUrl, mode, tls, channelBinding: "prefer" }, limits?)` expose the same `transaction(async tx => result)` / `close()` API. Imports and factory calls acquire no connection; there is no URL/env fallback, singleton, automatic migration, runtime selector or application import. Both use production **pg 8.23.0**; types remain development-only. No Neon SDK, `supabase-js`, CLI/local proxy stack, Neon Auth/Data API/Storage/Functions or HTTP API is used.

- Pass explicit server-controlled configuration privately, never request-supplied connection data. Local accepts loopback plus explicit port/non-TLS; the Neon endpoint/mode matrix below is separate. Both reject URL queries/fragments, missing credentials and malformed input without echoing it. Neon rejects unknown configuration/TLS/channel-binding keys. These restrictions are transport configuration, **not** authorization to connect, write, migrate or enable a deployment. The unchanged integration guard still requires a separately confirmed isolated local target and refuses every hosted URL.
- One checked-out client owns BEGIN, transaction-local timeouts, sequential queries, COMMIT/ROLLBACK and release. `tx.query(DrizzleSQL)` compiles parameterized Drizzle SQL and returns unknown row values to validate. Only trusted server-authored SQL belongs here: no client SQL, transaction-control commands, nested transactions or escaped query handles. Await every query and keep callbacks short/database-only; do not await external verification/network work inside them.
- Caught SQL errors still abort the transaction. Pending work is drained and rejected before release; overlapping queries and post-callback use are refused. A successful return requires an actual COMMIT response. Driver failures retain only phase/SQLSTATE; callback errors remain caller-owned and private. Rollback failure retains both errors in an `AggregateError`; broken/uncertain clients are discarded. A failed/lost COMMIT response has `commitOutcome: "unknown"`, even if a subsequent rollback succeeds: **no automatic retries**, no assumption that nothing was saved. Later operation receipts must reconcile that ambiguity.
- `close()` immediately refuses new transactions, drains accepted work, ends the owned pool and is idempotent. Always await it in `finally` within the operation/request lifetime; never retain pools across serverless requests. Driver shutdown is not a remote backend-cleanup acknowledgment: the local observer verifies actual TEMP-table removal within a bounded window. Idle driver-error events are consumed without secret-bearing logs; operational telemetry remains later work.
- Defaults (configurable positive integers, milliseconds capped at 2³¹−1 to avoid timer overflow): two connections (maximum ten), 3s acquisition, 5s SQL statement, 6s client-query, 1s lock and 5s idle-transaction timeout; idle pool connections expire after 1s. Client-query timeout must exceed statement timeout; lock timeout cannot exceed it. These bound DB waits, **not arbitrary JavaScript callbacks, total request duration or recovery targets**. Runtime request cancellation/deadlines and least-privilege roles remain service work.
- Every transaction sets timeouts **and UTC transaction-locally** using `set_config(..., true)` after BEGIN. `tx.query` sends only text/values to pg, never a named prepared-statement configuration. Trusted SQL must not issue `PREPARE`, transaction control, session-level `SET`/locks, LISTEN or rely on session state/TEMP tables surviving COMMIT. There is no SQL sandbox/parser; service authors own this contract.

### Neon transport configuration and limits

Based on current official Neon [connection selection](https://neon.com/docs/connect/choose-connection), [endpoint](https://neon.com/docs/connect/connect-from-any-app), [pooling](https://neon.com/docs/connect/connection-pooling) and [secure connection](https://neon.com/docs/connect/connect-securely) guides, rechecked on 2026-09-06:

| Explicit mode | Accepted endpoint and port                            | Intended use / limits                                                                                                                                              |
| ------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `direct`      | `ep-<endpoint-id>.<region>.aws.neon.tech:5432`        | Stable direct PostgreSQL sessions; use separate native direct tools for migrations, `pg_dump` and restore. Direct connections consume PostgreSQL connection slots. |
| `pooled`      | `ep-<endpoint-id>-pooler.<region>.aws.neon.tech:5432` | Neon PgBouncer transaction pooling for serverless/concurrent application traffic; backend affinity exists only inside each transaction.                            |

URLs require an explicit port/database, percent-encoded credentials and a simple SQL role name. Custom domains, arbitrary proxies, host-suffix lookalikes, Supabase/local targets, omitted/mismatched modes/ports and **all** query strings are refused. Choose the exact endpoint from the eventual project's Connect panel after authorization; matching its shape does not prove project ownership or role privileges. Node TCP/TLS runtime is required; this is not an Edge-compatible HTTP adapter.

`tls` must explicitly be `{ trust: "system" }` (Node's configured default trust roots) or `{ trust: "ca", ca: pemBundle }` (explicit PEM CA roots supplied by the authorized caller). The latter validates a bounded certificate-only CA bundle locally; it never reads a path or downloads a certificate. Neon currently uses a public ISRG root normally available in system trust stores. Both modes enforce TLS 1.2+, `rejectUnauthorized: true`, exact endpoint SNI and Node's standard hostname verifier. There is no insecure fallback, verification override or client-URL SSL parsing by pg. URL `sslmode` and `channel_binding` directives are rejected, not silently dropped; reconcile a copied Console URL with the explicit fields.

`channelBinding: "prefer"` enables pg 8.23.0's `enableChannelBinding` behavior: it chooses SCRAM-SHA-256-PLUS when offered and otherwise permits SCRAM-SHA-256. This is useful but **not** `channel_binding=require`. Mandatory channel binding would need a separately selected/proven client; the factory refuses a configuration labelled `require`. Verified TLS remains independent. Explicit startup fields prevent ambient PG connection/TLS/options/replication settings from substituting transport policy: whitespace-only `options` supplies no session settings, normal SQL replication mode is `false`, encoding is UTF8 and SSL negotiation uses PostgreSQL's SSLRequest. Hosted startup/authentication compatibility still needs proof.

Neon PgBouncer uses transaction mode. Session `SET`/locks, LISTEN/NOTIFY, cross-transaction TEMP state and SQL `PREPARE`/`DEALLOCATE` are outside this boundary. Current Neon supports protocol-level named prepared statements, so no provider-wide prohibition is claimed; this conservative adapter simply supplies text/values and therefore keeps application queries unnamed. Pool sizes depend on compute tier and every concurrent Vercel instance. The local maximum of ten is **not** a capacity plan, and Neon advises against unnecessary client-side pooling over its pooler. Verify runtime networking, project/free-tier limits, certificate/authentication behavior, pool exhaustion, cold-start latency, failure/commit ambiguity and cleanup before wiring it. Cross-request Vercel Fluid lifecycle and `attachDatabasePool` are later runtime work; request-owned close remains the current foundation.

### Hosted isolation prerequisite (not configured)

Before **any hosted migrations**, audit role memberships and existing/per-object-creator default privileges for schemas, tables, sequences and functions, including `PUBLIC` and security-definer/EXECUTE behavior. Use distinct least-privilege runtime versus migration roles: runtime must not have owner/admin, DDL/TRUNCATE, trigger-bypass or cluster-wide privileges. Verify private CMS/passkey/session/challenge tables have no browser or alternate API access path and confirm optional Neon Data API access is not enabled for them. Next.js passkey/session checks cannot protect a separate provider API.

Current `public` schema artifacts intentionally remain unchanged and do **not** implement this role posture. Later grant/schema hardening must be separately authorized, append-only and negatively tested. Neon Auth/Data API/Storage/Functions are not selected, and no platform settings, roles, grants, schemas or credentials were provisioned here.

## Required publication transaction/retry semantics (not implemented)

1. Authorize the operation/environment and validate strict input. For publication, look up its operation ID first. Compare the complete command and server-computed canonical request hash; a reused ID with different input is a conflict.
2. An identical committed retry returns its original receipt, not a new revision or write, even if newer decisions exist. Pending sync is not a success acknowledgment. The pure `publicationRetry` helper models only this decision.
3. For a new operation, lock/read the post and check **both** expected versions in the same transaction as the write (or a conditional UPDATE with a checked row count). The pure `checkExpectedVersion`/`canChangeSlug` helpers alone race and must never authorize an unchecked write.
4. Autosave updates only the draft and versions. Explicit save creates/selects a durable revision. Publish/republish selects the validated complete snapshot, locks the slug on first publication and changes the publication pointer. Restore changes only the draft; unpublish clears visibility but retains draft/history/slug lock.
5. Atomically persist the publication decision and its pending invalidation receipt. Invalidate **all** required detail/metadata/missing-slug/index/home tags, then persist synced state before reporting success. A commit followed by invalidation failure reports sync-pending, not success or “nothing saved.” Durable retries must not rely on one surviving serverless process or reapply an older decision over newer state.

No current database constraint proves those multi-row operations are atomic, that request hashing is correct, or that any cache invalidation occurred. Concurrent tabs/devices, lost responses, partial invalidations and hosted cross-instance freshness need step-3+ evidence.

## Dependencies, drivers and remaining gates

- zod supplies shared executable validation; Drizzle ORM supplies typed PostgreSQL definitions; Drizzle Kit supplies generated migration artifacts. Node 24's native test runner/type stripping avoids another direct test-runner dependency. `cms/package.json` scopes ESM locally; TypeScript permits explicit `.ts` imports without changing root app module semantics.
- Existing production `pg` 8.23.0 supplies both Neon SQL/TLS and local adapter capability; `@types/pg` 8.23.1 and Drizzle's node-postgres migrator remain development/test-only. Drizzle's upstream optional-peer metadata is not an installed Neon SDK, and neither a Neon nor Supabase SDK is resolved. No app/build-time connection or hosted verification is claimed.
- Drizzle Kit brings esbuild transitively. pnpm explicitly denies esbuild postinstall downloads, as it already denies unrelated package scripts; generation works with the platform optional binary. The frozen install and generation commands were exercised. Upstream deprecated esbuild-kit dependencies remain Drizzle Kit's dependency chain, not an added application compiler pipeline.
- The additive [auth-data foundation](studio-auth-foundations.md) now defines singleton owner, credential, session and challenge records with token/eligibility tests and migrations `0002`/`0003`. Local PostgreSQL constraint execution is now proven; real authentication is not. Media/storage tables, runtime auth/environment/cookie/CSRF wiring, authorized seeds and localhost WebAuthn mode remain step-2/3 work; the isolated CI database job is configured but not hosted-run; do not add unused hosted SDKs merely to complete a checklist.
- No real writing/photos until the plan's automated database/media backups, isolated restore drill and export/import checks pass. Recovery targets and owner-operated procedures still need defining and measured verification. Security, hosted five-second invalidation and recovery gates are unchanged by these unit tests.
