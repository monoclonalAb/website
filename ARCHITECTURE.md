# Architecture

Eric Zheng's personal site: a split-alphabet home page plus About, Blog, Contents, Changelog, Leetcode, Friends and Books pages, and an unlisted invitation to Eric's 2026 birthday dinner. Plain HTML, CSS and JavaScript, built from Markdown by a bash script and pandoc, and served by Vercel as static files. Two small Vercel Functions keep what readers send: `api/comments.mjs` the comments on blog posts, and `api/subscribe.mjs` the list of readers who get an email about each new blog post.

## How a page gets built

1. Eric commits Markdown to `content/`: blog posts, Leetcode entries, the changelog, the list of About photos and the books he's read. [docs/writing.md](docs/writing.md) has the format.
2. `make` runs `build.sh`. It checks every file in `content/`, turns the Markdown into HTML with pandoc, and wraps it and the copy in `pages/` in the shared head, masthead and footer. Each page goes in its own folder in `out/` (`out/blog/page/2/index.html`), beside the feed, the sitemap and a copy of `public/`. It builds the new site in a folder beside `out/` and swaps it in at the end, so `out/` never holds half a site, and a failed build leaves the last one that built. Builds take turns through a lock, `out.lock`. `build.sh --update`, which `make serve` runs on every save, redoes in place only the pages that show the files changed since the last build, in under a second; the end of `build.sh` lists which pages each file feeds.
3. A file that breaks a rule stops the build and names the file: a misspelt frontmatter key or page setting, raw HTML, a photo that still has camera data, or a book without a cover.
4. Vercel runs the same build (`vercel.json`), with pandoc from `scripts/install-pandoc.sh`, serves `out/`, and runs `api/comments.mjs` at /api/comments and `api/subscribe.mjs` at /api/subscribe. `vercel.json` also redirects the old static site's links, and the page-number field's `?page=N` when JavaScript is off.
5. In the browser, five small scripts in `public/js/` add the edge waves, index pages that hold as many entries as fit on the screen (which also opens an old changelog link on the right page), the page-number field's in-place jump, the fade-out of the photo sheet and of a picked book, and a blog post's comments, which they fetch from /api/comments. Every page reads fine without them, and the comment form and the sign-up send without them.

## Invariants

Most of these are things that are absent, so they're easy to break without noticing.

- JavaScript runs only from the five files [AGENTS.md](AGENTS.md) lists, and pages in `pages/` carry no scripts of their own (Home's structured data aside; `build.sh` writes each post's). `make docs` fails otherwise.
- Markdown never runs code: `build.sh` rejects raw HTML and `#` headings, and there's no MDX.
- Writing lives in `content/`, photos in `public/photos/` and book covers in `public/books/`; page copy lives in `pages/`, the comment section's and the sign-up's copy in `comments_section` and `subscribe_form` in `build.sh`, and the emails' in `emails/`. Nothing is fetched from a service when a page is viewed, except a blog post's comments from /api/comments.
- Comments are plain text: the function stores what was typed, and `public/js/comments.js` sets it with `textContent`, never as HTML. A commenter's email waits with the comment until Eric approves or deletes it, and is never shown or kept beyond that.
- A subscriber's email address is kept until they unsubscribe, is never shown on the site (only `make subscribers` lists it, for Eric), and is used for nothing but the emails about new posts. The confirm and unsubscribe links carry a random token, never the address, and the functions never log one.
- There are two post sections: `blog` (`content/blog/<slug>/index.md`, images beside it) and `leetcode` (`content/leetcode/<slug>.md`). `read_posts` in `build.sh` knows each one's files and frontmatter.
- Frontmatter is read strictly, so an unknown or misspelt key fails the build. It's a small part of YAML: `key: value` lines, plain, 'single' or "double" quoted, and `#` comments.
- So is the comment at the top of each page in `pages/` (`check_pages` in `build.sh`): `<!--` and `-->` on lines of their own, and between them `key: value` lines with the keys `title`, `description`, `nav`, `main`, `css`, `js` and `layout`. Each `css` and `js` name must be a file in `public/css/` or `public/js/`. A page needs a title and a description unless it has a `layout` (`home` or `bare`).
- Prettier leaves `pages/` alone (`.prettierignore`), because the copy there is wrapped by hand.
- Heading ids keep the Next.js site's rule (lower case, each run of other characters a hyphen, `-2` and `-3` on repeats), because links to them are out in the world. `build.sh` sets them, not pandoc.
- Photos never carry camera data, which can say where they were taken: `scripts/photos.sh` strips it, and `build.sh` refuses a JPEG that still has it. Each photo needs its 320px and 640px copies, which `make photos` makes.
- The build writes the same site on macOS and Linux: portable bash, awk and sed, and `LC_ALL=C`.
- `content/` images are served only from `/writing-assets/`.
- An update (`build.sh --update`) leaves `out/` exactly as a whole build would. It finds what changed by comparing every source file's checksum with `out.sources`, which the last build that worked wrote, and redoes the pages each changed file feeds, as listed at the end of `build.sh`; a post's indexes only when its line in `out.posts.tsv` (title, date, summary) changed, and the posts either side of one that's new, gone or retitled, since each post links to the posts before and after it. If you make a page show something from another file, like a post's text on the index, add it to that list. Changing `build.sh` itself builds the whole site. An update checks everything it reads before it writes anything, and one that fails partway deletes `out.sources`, so the next build is a whole one.
- Old links keep working. The static site's URLs redirect in `vercel.json`, and a changelog entry keeps its `#changelog-<date>` anchor and feed guid after newer entries push it onto a later page.

## Checks

`make check` is what CI runs (`.github/workflows/ci.yml`): shellcheck, a syntax check of the functions in `api/`, `make docs` and a build. There are no unit or browser tests. The build is the content test, because `build.sh` checks every file it reads.
